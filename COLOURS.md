# Scope colours and their purposes

What every TextMate scope this grammar assigns actually means, why that scope was chosen, and what colour it resolves to. This exists because that reasoning was previously scattered across `TODO.md`'s dated sections and commit messages rather than collected in one place (see `TODO.md`'s "Document all scope colours and their purposes" entry).

**Keeping this in sync**: the authoritative, always-current source is `scripts/resolve-theme-colors.js`, which auto-discovers every scope directly from `syntaxes/testcontrolprotocol.tmLanguage.json` and resolves its real effective colour against a theme (following `"include"` chains and TextMate specificity rules — "has a colour rule" and "renders as a visually distinct colour" are different questions, see the Light+/Dark+ collision this tool caught in `TODO.md`'s "Label colour unification" section). Run it after any grammar change that adds/removes a scope:

```
node scripts/download-themes.js         # once, to fetch theme JSON
node scripts/resolve-theme-colors.js dark_plus.json light_plus.json
```

The hex values below were captured this way on 2026-07-31. If they've drifted from what the tool reports now, trust the tool, not this file.

## Colour-bearing (capture) scopes

These are the scopes actually assigned to specific *captured tokens* — the ones a theme visibly colours differently. There are 11 distinct scope names in use, resolving to **8 visually distinct colours** (one group of three, and one pair, collide — noted below).

| Scope | Dark+ | Light+ | Purpose |
|---|---|---|---|
| `entity.other.attribute-name` | `#9cdcfe` (light blue) | `#e50000` (red) | The single-letter **line-type marker** immediately after the margin — `I`, `A`/`M`, `N`/`R`/`S`, `H`. (Not used for `D`/`T`/`Q`/`GLOBAL`'s own marker — see "Intentional divergences" below.) |
| `keyword.control` | `#C586C0` (purple) | `#AF00DB` (purple) | The **instruction keyword** on an I-line — `GOTO`, `GOTCP`, `SEARCH`, `NORMALX`, `PRINT`, `CR TEST`, `REQPRIOR`, etc. Never used on A/M/N/R/S/D/T/Q/`GLOBAL` lines, since those aren't instructions. |
| `entity.name.function` | `#DCDCAA` (yellow) | `#795E26` (yellow/brown) | **Branch labels** — both declarations (an I-line's own label field) and references (a `GOTO`/`GOSUB`/`SEARCH`/`GETSPEC`/etc. target, `CR TEST`/`CR CRS`/`CR REQ`/`CR REQL`'s op2/op3) share this one colour *deliberately* — see "Label colour unification" in `TODO.md`: they're both "a label," and splitting them by declaration-vs-reference was tried and explicitly reverted per user direction. Also used for `H`-line's own data-box label — see "Known inconsistency" below, since this is arguably the wrong namespace for it. |
| `storage` | `#569cd6` (blue) | `#0000ff` (blue) | **Data declarations and references that resolve to one** — `A`/`M`-line's own label, `N`/`R`/`S`-line's own label, and any operand confirmed to reference a declared data box (`NORMAL`/`GROUP`/`CR COM`/`CR TEST`/`CR CRS`/`CR REQ`/`CR REQL`'s data operand, `PRINT`'s op2, `GOTO,IR`'s op3 range reference). The operand deliberately matches the colour of the label it points to, tying reference to declaration visually. |
| `support.type` | `#4EC9B0` (teal) | `#267f99` (teal) | **Cross-file / global identity tokens** — a `T`/`Q` title's own test code and name, a macro definition's own name (`D <name>`) and its own `D` marker (the one marker-letter exception, chosen to match the macro name — see "Intentional divergences"), the `GLOBAL ALPHA DATA` header, `GOTCP`'s cross-file target, `NORMALX`'s op1 test-code reference. The common thread: these all identify something meaningful *outside* the current I-line's own block-local label namespace. |
| `string` | `#ce9178` (orange) | `#a31515` (orange/red) | The general-purpose **value/free-text field** bucket — title's long description, number-line's numeric range values, alpha-line's character-string value, a comparison/flag operand (e.g. `GOTO`'s condition value, `GOTCP`'s flag), and validated small fixed-vocabulary fields once they match (`NORMALX`'s 6-word global-date enum, `SEARCH`'s 13-word item keyword). By far the largest, least specific bucket. |
| `string.control` | `#ce9178` (orange) — **collides with `string`** | `#a31515` — **collides with `string`** | `H`-line's own hex-constant value only. Chosen as a more specific scope than plain `string` (presumably to allow a future theme/rule to distinguish "control/hex data" from generic text), but no theme checked here actually does — it renders identically to plain `string` today. Functionally interchangeable with `string` right now. |
| `comment.line` | `#6A9955` (green) | `#008000` (green) | Full `*`-prefixed comment lines, and every rule's own trailing catch-all group — whatever's left on the line after every declared field is accounted for, up to column 80 (see `TODO.md`'s "Trailing/overhanging comments enabled" section for why this is intentionally *not* `invalid`). Also `D`-line's own trailing note field. This is the scope an unrecognized enum value used to fall into before 0.15.0, which is exactly why an invalid `NORMALX`/`SEARCH` value used to render green instead of red. |
| `invalid` | `#f44747` (red) — **collides with the two below** | `#cd3131` (red) — **collides with the two below** | Three separate uses, all rendering the same red: (1) `A`-line's declared value overflowing its own field width, (2) `NORMALX`'s op2 when it's present but not one of the six documented global dates (0.15.0), (3) `SEARCH`'s item keyword when it's present but not one of the 13 documented words (0.15.0). |
| `invalid.illegal-character` | `#f44747` — **collides with `invalid`** | `#cd3131` — **collides with `invalid`** | Column 7 (the last column of the fixed 7-char margin) contains a non-whitespace character, where the format requires it to be blank. |
| `invalid.too-long` | `#f44747` — **collides with `invalid`** | `#cd3131` — **collides with `invalid`** | The whole line exceeds 80 characters. Checked *before* any other rule (the `invalid` include is first in `patterns`), which is what makes the "trailing comments allowed up to column 80" feature work at all — see `TODO.md`'s "Trailing/overhanging comments enabled" section. |

The three `invalid*` scopes and the `string`/`string.control` pair are the two places this grammar assigns more than one scope name to what a theme actually renders as one colour. That's an accepted, understood state (documented here precisely so it doesn't get "discovered" again as a surprise) — not a bug: the sub-scopes exist so a future theme *could* distinguish them, and `resolve-theme-colors.js`'s COLLISION flag is what confirms none currently do.

## Known inconsistency, not yet resolved

**`H`-line's own label uses `entity.name.function` (the label colour), not `storage` (the data colour) — even though `src/labelParser.js` treats `H` exactly like `A`/`M`/`N`/`R`/`S` for every diagnostic purpose** (`findDataDeclarations` collects all six line types into the same namespace; `H` boxes are referenced and validated identically to `A`/`N` boxes). This dates back to before the diagnostics feature existed (see the `331059b` commit, which explicitly grouped "hex-lines' data-box label" together with I-line's own branch label as a "declaration," a decision made when this grammar only had highlighting, no semantic diagnostics yet, and had no reason to think of `H` as belonging to the same category as `A`/`N`). The result: a hex constant's declaration visually reads as if it were a branch label, not a data box, even though it behaves exactly like one. Left as-is here (documenting, not silently changing shipped highlighting) — worth a deliberate decision (most likely: recolour `H`-line's own label to `storage` for consistency) next time colours are revisited.

## Intentional divergences (not inconsistencies — deliberate, on record)

- **The `D`-line's own marker is `support.type` (teal), not `entity.other.attribute-name` (light blue) like every other line type's marker.** Per commit `d5de510`, made teal specifically to match the macro name it introduces, on request.
- **`T`/`Q` title-lines and the `GLOBAL` header have no separate "marker" capture at all** — their own code/header text *is* the identifying token, captured directly as `support.type`, rather than splitting a marker letter from a following field the way every other line type does.
- **Declarations and references share one label colour on purpose** (`entity.name.function` for both) — see the "Label colour unification" entry in `TODO.md`. This was tried the other way first (two distinct scopes) and explicitly reverted.

## Line-level (non-colour-bearing) scopes

Every rule also assigns a `name` to the *whole matched line span* (e.g. `instruction-line.testcontrolprotocol`, `alpha-line.testcontrolprotocol`, `title-line.testcontrolprotocol`, `hex-line.testcontrolprotocol`, `number-line.testcontrolprotocol`, `macro-definition-line.testcontrolprotocol`, `global-header-line.testcontrolprotocol`). No theme checked here assigns these a colour of their own — the more specific capture scopes nested inside always win. They exist as a structural/semantic label for the line as a whole (useful for folding, future language-feature providers, or a future theme that specifically wants to target "every instruction line" as a unit), not for colouring. `instruction-line.testcontrolprotocol` in particular is shared by *every* I-line rule (`goto-lines`, `search-lines`, `gotcp-lines`, `simple-branch-lines`, `normalx-lines`, `data-reference-lines`, `cr-report-lines`, `print-data-reference-lines`, `instruction-lines`) — they're different TextMate rules (different match patterns, different capture layouts) but the same conceptual "kind of line."

## What's still unused / open

No scope in this grammar's current or past history (checked via `git log --all -p`, see `TODO.md`'s colour-taxonomy section) resolves to grey under Dark+ or Light+ — if a future feature wants a distinct "implicit global/system field" colour (as opposed to the `storage` blue currently shared with genuine user-declared variables — see `TODO.md`'s "Colour taxonomy" entry, still open), it needs either a genuinely new scope choice or VS Code semantic highlighting (which has the full workspace-index context this static grammar doesn't). Confirm any newly-proposed scope against `scripts/resolve-theme-colors.js` before adopting it — that's precisely the check that's been skipped and caught as a real bug twice already in this grammar's history (see "Label colour unification" in `TODO.md`).
