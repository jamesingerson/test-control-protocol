## Grammar correctness

- [x] **Title-line scope mislabelled as `hex-line`.** `title-lines` was created by copy-pasting `hex-lines` (confirmed via `git show 53a899c`) and its overall scope name was never updated. Fixed in `syntaxes/testcontrolprotocol.tmLanguage.json` — now `title-line.testcontrolprotocol`. Caught by the new snapshot tests before it could get baked in as "expected" behaviour.
- [x] **Highlighting silently disappearing for some users, depending on colour theme.** `support.type`, `variable.parameter`, and `entity.name.function` have no colour rule at all in VS Code's bundled "Visual Studio" legacy themes (`dark_vs.json`/`light_vs.json`), only in the modern Dark+/Light+ defaults — confirmed by diffing the grammar's scopes against VS Code's own theme source. Remapped to scopes with real coverage in both: `support.type` → `storage.type`, `variable.parameter` → `entity.other.attribute-name`, `entity.name.function` → `entity.name.tag`.
- [x] ~~Trailing literal `\n` in `invalid`/`comments` match patterns could fail to match the last line of a file lacking a trailing newline~~ — investigated empirically via `vscode-tmgrammar-snap` (the real VS Code tokenizer) across single-line files, multi-line files, with and without a trailing EOF newline. All matched correctly in every case tested. Not an actual bug — no action needed.
- [x] **`goto-lines` keyword alternation was inconsistent.** Fixed: wrapped the alternation in `(?:...)` so `\b`/`\s` apply uniformly to all four keywords, and capped `SEARCH` at the same 8-char field width as the others. Verified via the snapshot tests — the keyword field now spans its full 9-column width instead of leaking a stray space into the next field.
- [x] **Folding markers didn't match the grammar's own column convention.** Fixed: `language-configuration.json` now uses the fixed `.{7}` line-number field and includes `Q` as a valid title-line type in the fold start marker. Not covered by the snapshot tests (they only exercise tokenization, not folding) — worth a manual F5 check.
- [x] **`get-lines` duplicated `goto-lines`.** Its capture-scope mapping was byte-identical to `goto-lines`'s, so `GET` is now folded into the same keyword alternation instead of being a separate copy-pasted block. `gotcp-lines` and the generic `instruction-lines` fallback stay separate by design (each assigns a genuinely different scope to at least one field) — considered restructuring them into nested begin/end sub-patterns to share more code, decided against it: no visible benefit, and it would introduce a structural pattern (begin/end) not used anywhere else in this grammar for the sake of DRY alone.

- [x] Confirmed **correct, not a bug**: `gotcp-lines` coloring the GOTCP target as `storage.type` rather than `entity.name.tag`. The manual confirms GOTCP's operand is a 4-digit numeric test code, not a label — resolves the open question left in the duplication item above.
- [x] **SEARCH's item operand is a fixed 12-word vocabulary, not free text** (`PATIENT NAME REQUEST DATETIME ARRSET REPORTED TRACKED TEST GROUP CONSTIT ANTIBODY PRODUCT TESTDEPT`) and was colored as generic `string`. - [x] **Condition-code suffixes on GOTO/GOSUB were unvalidated** — any 1-4 char suffix was accepted as `keyword.control`. ### Cross-checked against real production data (2026-07-30)

The user confirmed `TCP/MACRO` and `TCP/GLOBAL` are both genuinely opened with this extension, and pointed at the real production TCP repo (`C:\repos\TCP`, read-only — not to be modified). Precisely column-anchored scans (not loose text search, which produced false positives at first — e.g. an unanchored check made bare `DATE` look common when it was actually always appearing as an operand *value* like `PRINT 21 DATE`, never as the instruction keyword) across ~378 files / 100k+ lines:

- [x] Every GOTO/GOSUB/DATE/GET/GOTCP condition-code suffix actually used in production matches the tightened, documented set exactly — zero unrecognised suffixes found. Confirms the item-5 tightening above doesn't reject anything real.
- [x] SEARCH's item-operand word is always one of the documented 12, and SEARCH never takes a condition-code suffix (2638 real occurrences, all bare `SEARCH`) — confirms the search-lines split above.
- [x] **`D` lines fixed.** Real `D`-lines in `MACRO` confirmed the manual's shape (macro name, not code+name+units) but revealed an extra undocumented detail: an optional free-text note can follow the name (e.g. `D BLANKMC1 NEWLINE`), with no fixed column boundary for where it starts — some names fill the full 8-char field with no gap at all before the note. `title-lines` no longer matches `D` (now just `[TQ]`); added a dedicated `macro-definition-lines` rule using `[^ ]{1,8}` for the name (stops at the first space naturally, unlike `.{1,8}\s` used elsewhere, which would either fail to match names with no trailing content at all or risk swallowing into the note on short names — verified this matters using a real short-name+trailing-content shape). Verified against the entire real `MACRO` file (13,638 lines) — zero unstyled spans.
- [x] **`G` lines fixed.** The real `GLOBAL` file's header line is literally the text `GLOBAL ALPHA DATA` starting at column 8 (the `G` of "GLOBAL" *is* the type-code character) — confirmed exactly as the manual described. Added a `global-header-lines` rule matching that literal, scoped `markup.heading`. Verified against the entire real `GLOBAL` file — zero unstyled spans.
- [x] **`M` line format: decided to accept the current `A`/`M` merge as-is, unresolved by design rather than by evidence.** Searched the entire real production repo (~378 files) for a column-8 `M` line and found zero (the single early `M` hit was from `.gitignore`, not a TCP file); the manual only implies Mask lines exist via error messages (Reference Manual Assembly Error 35, p.314; System Errors 15/16/24, p.317) without ever specifying their format. No real data exists either way to confirm or refute the merge. User's call: Mask lines are likely a meta/utility feature for the third-party vendor's own development use, not something authored by end users at Pathlab — so the current merge is accepted permanently rather than left as a pending question. Do not re-raise this in future reviews unless a real `M`-line example actually surfaces.
- [x] All four real files spot-checked (`GLOBAL`, `MACRO`, `HAEM`, `BIO`, one `SEARCH/` file — ~38,000 lines combined) tokenize with **zero unstyled spans** after the D/G fixes (excluding the line-number field, which is deliberately uncoloured by design).
- [x] **Trailing comments past column 55 flagged `invalid` (red) — confirmed intentional, not a bug.** The manual documents column-55+ free text as a legal inline comment, and real `HAEM`/`BIO` lines use it (e.g. `I COPY     COPYTO   51456                          copy to Hosp PHAR`). Raised this as a cross-cutting finding since every rule's final catch-all group scopes that region `invalid.testcontrolprotocol`. The user confirmed this is a deliberate choice, not an oversight: the real-world implementation of trailing comments is poor and creates ambiguity and compilation errors, so flagging them as invalid is intentionally discouraging their use even though the format nominally permits them. No change needed — do not re-flag this in future reviews.
- [x] **Title-line field widths were not just imprecise — they were actively too narrow, wrongly flagging real content invalid.** The old regex budgeted 18+19=37 characters total for name+units combined (from col13); the manual's real column layout (name cols 14-29, units cols 31-50) needs 17+20=37... but that's only correct when both fields are used. Real data showed a third, undocumented case: **when a title has a long descriptive name and no units at all, authors just let the name run past col29 with no separator** — confirmed directly (`T0013 ES300 General Link    - Look at TCP/LINK`, `T0527  HORMONE TESTS...   Pathlab WCP`, etc.). Quantified impact: **51 of 3977 real `T`/`Q` lines (~1.3%) had legitimate trailing text (`- Look`, `Ref Range`, `Pathlab WCP`, `Porphyrins`, ...) wrongly rendered `invalid` (red) today**, not a theoretical precision gap. Fixed by widening the two fields (17 + 62 chars) so nothing legitimate on a well-formed ≤80-char line can fall past them into the overflow group — verified against all the real overflow examples found, all now render with zero `invalid` spans. Also tightened the code field from `.{4}` to `\d{4}` since all 3977 real codes are purely numeric, with zero exceptions.
- [ ] **GOTO/label verification feature** — feasibility confirmed, not yet scoped or built. Labels are scoped per-TCP-file (flat namespace), forward references are legal, and "undefined label"/"duplicate label" are real, named assembler errors (Errors 14 and 5 respectively) — meaning a diagnostics feature (flag GOTO/GOSUB/GET/SEARCH-op1 references with no matching in-file label definition, or a label defined twice) would mirror the real assembler's own checks, not a fuzzy heuristic. Bigger scope change than anything done so far: needs actual extension activation code (`main` entry point, `activationEvents`, `vscode.languages.createDiagnosticCollection`), not just a declarative grammar — needs a real design/scoping conversation before starting.

## Label colour unification (2026-07-30)

- [x] **`entity.name.tag` was used for both a label declaration (an I-line's own label) and a reference to a label (a GOTO/GOSUB/DATE/GET/SEARCH target) — same colour.** Initially misread as a bug needing a split (see the false-start below); the user clarified the actual goal is the opposite — declarations and references should intentionally share one colour (they're both "a label"), just not the *original* colour, since that also collided with other unrelated scopes. Final state: both now use `entity.name.function`, confirmed via `scripts/resolve-theme-colors.js` to render as a colour (`#DCDCAA` Dark+, `#795E26` Light+) genuinely distinct from the marker (`entity.other.attribute-name`), `keyword.control`, `string`, `comment`, and `invalid` — the things it actually needs to be distinguished from.
- **False start, corrected**: first tried splitting declaration/reference into two scopes (`entity.name.tag` + `variable.language`, then `entity.name.tag` + `entity.name.label`) before the user clarified the real goal was unification, not separation. Along the way this surfaced a real, separate methodology bug: `variable.language` was verified as having a colour *rule* in `dark_vs.json`, but never checked against whether that rule's actual hex value differed from `entity.name.tag`'s — it didn't (both `#569cd6`), and since `dark_plus.json` only *includes* `dark_vs.json` without overriding either scope, the collision carried through to Dark+ too. **Lesson, now encoded in `scripts/resolve-theme-colors.js` rather than just written down**: "has a colour rule" and "renders as a visually distinct colour from another scope in use" are different checks.
- [x] **Added `scripts/resolve-theme-colors.js`** (+ `scripts/download-themes.js` to fetch the theme JSON it reads) — resolves the actual effective colour VS Code would render for every scope this grammar uses, against a given theme, following `"include"` chains and real TextMate specificity rules, and flags any of our own scopes that collide. Run `node scripts/download-themes.js` once, then `node scripts/resolve-theme-colors.js [theme files...]`. This is what caught the `variable.language`/`entity.name.tag` collision precisely, after two LLM-summarized web-fetches of the same file gave contradictory answers about the exact same string ("does dark_plus.json override `storage.type`?") — parsing the raw JSON directly resolved the ambiguity for good. Use this tool for any future colour-collision question on this grammar instead of guessing from memory of past fetches.
- [x] **Two more instances of the same "coverage fix regressed the Dark+ colour" mistake, caught by the user reviewing real content.** Both `storage.type` (title-line code/name, GOTCP target) and `constant.language` (SEARCH's item keyword) were teal/orange respectively before an earlier session pass moved them to fix legacy `dark_vs`/`light_vs` coverage gaps — that fix cost the Dark+ colour without checking what it actually became. Confirmed via `scripts/check-one-off.js` (ad-hoc, not committed) that `support.type` restores the teal (`#4EC9B0` Dark+, `#267f99` Light+, unstyled on legacy `dark_vs`/`light_vs` — same accepted tradeoff as `entity.name.function`) and plain `string` restores the orange for SEARCH's item keyword. Reverted `storage.type` → `support.type` (title-lines, gotcp-lines) and `constant.language` → `string` (search-lines). This also shrank the previously-logged 4-way Dark+ collision down to just `markup.heading`/`storage` (`#569cd6`) — the `G`-line header and number/alpha-line's own label — a much smaller, lower-stakes residual gap, still open below.
