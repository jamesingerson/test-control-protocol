## Number-line (`N`/`R`/`S`) field boundary bug (2026-07-30)

- [x] **`invalid` was starting at different columns depending on whether the trailing annotation text happened to look numeric.** The old regex matched each of the up to 4 numeric fields by *content* (`[+-.]?\d*[+-.]?\d*\s+`), and every component of that pattern is individually optional — meaning it would happily match a phantom "field" out of nothing more than "starts with a digit/sign/dot, then some whitespace." Real content confirmed this precisely: a trailing annotation like `1-3   "` or `70  Years` (both start with something digit-like) had its leading run swallowed as a fake 4th data field, leaving only the non-numeric tail (`"` or `Years`) marked `invalid`; an annotation like `< 1 month` or `adult` (starts with a non-digit) correctly fell into `invalid` in full. Same start-line, different end result, purely by coincidence of the first character.
- User's call: "make it naïve and consistent" — stop trying to recognise numbers by content, use pure fixed-width positional fields instead (the `.{1,8}\s` idiom already used for every other field in this grammar), so the boundary is the same real column regardless of content. Two iterations to get right:
  1. First pass made only 3 of the 4 fields require a trailing separator, leaving the last one width-capped but not separator-anchored — this let *short* trailing text (`adult`, 5 chars) fit entirely inside the last field's own slot and render as plain `string` with no `invalid` at all, while longer text (`70  Years`, 9 chars) only partially overflowed into `invalid`. Caught this myself before committing and flagged it as a real trade-off.
  2. The user's real screenshot showed neither the original bug's behaviour *nor* that first-pass trade-off — everything rendered fully `invalid` regardless of length, meaning the real file's field spacing is wider than my synthetic test fixture assumed. Made all 4 fields require the same trailing separator (`.{1,8}\s` × 4, matching the standard 9-char field width used everywhere else in this grammar), and rebuilt the fixture with realistic (fully 9-char-padded) spacing to match. Confirmed against the corrected fixture: both `70  Years` and `adult` now render fully `invalid`, matching the real screenshot exactly.
- **Lesson**: a synthetic fixture's exact spacing matters as much as its content when testing a positional/column-based grammar — a fixture padded too tightly can pass tests while silently not exercising the real-world column layout, producing a false sense of verification. Worth erring toward generous, standard-grid spacing (9-char fields, matching `editor.rulers`) in fixtures rather than the tightest spacing that happens to fit the sample values.

## Label and GOTCP verification feature (2026-07-30)

Built on explicit instruction, with scoping confirmed up front via three quick questions (trigger timing, GOTCP validation scope, `~`-label handling), then developed autonomously against real production data. First real extension-activation code in this repo (`main`/`activationEvents` in `package.json`, `vscode.languages.createDiagnosticCollection`) — everything before this was a declarative grammar only.

**Architecture** (plain JS, no build step, matching the rest of this repo):
- `src/labelParser.js` — pure regex-based extraction (label defs, GOTO/GOSUB/DATE/GET/SEARCH-op1 references, GOTCP targets, macro-invocation opcode fields, T/Q-block boundaries, D-macro-block boundaries). Regexes are hand-mirrored from the exact `.tmLanguage.json` match patterns (`goto-lines`/`search-lines`/`gotcp-lines`) so highlighting and diagnostics never disagree about what counts as a keyword/target/field. No `vscode` dependency — unit-tested with plain Node (`tests/label-parser.test.js`).
- `src/diagnostics.js` — pure orchestration: given a document's lines (+ optional macro/GOTCP workspace index), returns plain diagnostic descriptors. Unit-tested (`tests/diagnostics.test.js`).
- `src/workspaceIndex.js` — pure aggregation of macro-name→labels and test-code sets across a list of already-read `{uri, lines}` documents. Unit-tested (`tests/workspace-index.test.js`).
- `src/extension.js` — the only `vscode`-dependent file. Debounced on-change diagnostics per open document (~500ms), debounced workspace-index rebuild on file save/create/change/delete (~1000ms). Not unit-testable without a real Extension Host; verified with `node --check` (syntax only) and careful manual review against the real `vscode` API — **not exercised live in an actual Extension Development Host**, since this session has no GUI access to VS Code. Worth a manual F5 sanity check.

**Two corrections that came from validating against the real production repo (`C:\repos\TCP`, read-only) before trusting the design, both load-bearing — skipping either would have made the feature actively wrong, not just imprecise:**

1. **Labels are scoped per T/Q test-definition block, not per physical file.** A single file can bundle hundreds of scripts — `BIO` alone has 623 separate `T`/`Q` headers in one physical file. Naively treating "duplicate label" as "same label name anywhere in this file" produced 2063 false positives in that one file alone (e.g. `FIN` legitimately reused as a per-test terminal label 532 times). Scoping every check (duplicate labels, undefined labels) to the span between one `T`/`Q` header and the next dropped that to zero across the entire real corpus.
2. **Macro invocations inject labels into the calling block at assembly time.** A bare instruction line like `I DRUGM DRUGMCR` isn't a GOTO/SEARCH/GOTCP — `DRUGMCR` is a macro name (defined elsewhere, e.g. the real `MACRO` file, via `D DRUGMCR`), and its body's own labels (`CONT`, `DCHECK`, `ENDMCR`, ...) become valid targets inside any block that invokes it, even though they never appear in that block's own text. Confirmed via a real case: `BIO`'s `T0750` block references label `CONT`, which only exists inside the `DRUGMCR` macro it calls. Fixed by indexing every macro's internal labels workspace-wide and unioning them into a block's known-label set whenever that block's opcode fields match a known macro name. Related: macro *bodies themselves* are template code using an `OP1`/`OP2`/`OP3`/... parameter-placeholder convention (substituted by the caller's real arguments at assembly time) — confirmed in the real `MACRO` file (e.g. `D DTCP,EQ` contains `GOTCP,EQ OP1 ...`). Diagnostics deliberately never run *inside* macro bodies for this reason; only inside `T`/`Q` blocks.

**Validation**: after both corrections, ran the actual `diagnostics.js`+`workspaceIndex.js` end-to-end against the entire real production corpus (26 files, 3815 test blocks, 253 macros) — **zero diagnostics produced**, i.e. zero false positives against known-good, currently-running production scripts. This is the strongest evidence available that the feature's core logic is sound, short of live use.

**Live false positive found and fixed (2026-07-30, after initial build):** a real GOTCP reference in production file `CONTROL` (`GOTCP 4998`, targeting `T4998` which is defined in a completely different file, `HAEM`) was flagged as not found. Root cause: `getWorkspaceGlobPatterns()`/`collectWorkspaceUris()` fed `files.associations` pattern strings (e.g. `"**/TCP/**/*"`) directly into `vscode.workspace.findFiles()`. That API matches its glob against each file's path **relative to the workspace root**, while `files.associations` matches against a file's **full path** — different semantics. When the workspace root is opened as `C:\repos\TCP` itself (as it is for the real production repo), no relative path ever contains a `TCP` segment, so `findFiles('**/TCP/**/*')` silently matched zero files, and the workspace index quietly degraded to "whatever's currently open" — `HAEM` wasn't open, so `T4998` was invisible. Fixed by adding `src/globMatch.js` (pure, unit-tested glob matcher) and scanning broadly with `findFiles('**/*')`, then matching each result's full path against the association patterns ourselves, exactly mirroring how `files.associations` actually resolves. See `tests/glob-match.test.js`, which reproduces the exact real pattern/paths from this bug report.

**Known limitations, not fixed here:**
- No macro-expansion beyond label-name injection — a macro's internal `GOTO`/`GOTCP` references (which use `OP1`/`OP2`/`OP3` placeholders) are never themselves checked, by design (see above).
- `~`-prefixed macro-internal labels (disambiguated to `~1`/`~2`/... only at assembly time) are exempted from every check, not partially validated.
- The regex duplication between the grammar and `labelParser.js` (noted in that file's header comment) has no automated check tying them together — if one changes, the other must be updated by hand.
- The workspace-wide file index relies on `files.associations` (since real production TCP files are extensionless — `BIO`, `MACRO`, `GLOBAL` have no `.tcp` suffix); if a user hasn't configured any association for this language, workspace-wide GOTCP/macro resolution silently degrades to only the currently-open documents. Diagnostics for a document's own internal labels are unaffected either way.

## Workspace file discovery bug (2026-07-30, found from real use after shipping)

- [x] **`vscode.workspace.findFiles()` and `files.associations` use different path-matching semantics.** A real false positive: `GOTCP 4998` in production file `CONTROL` was flagged as not found, even though `T4998` genuinely exists in a different file, `HAEM`. `collectWorkspaceUris()` fed `files.associations` patterns (e.g. the real pattern `"**/TCP/**/*"`) straight into `findFiles()`, which matches its glob against each file's path **relative to the workspace root** — but `files.associations` matches against a file's **full path**. Since the real workspace root is `C:\repos\TCP` itself, no relative path ever contains a `TCP` segment (the root's own name is excluded from every relative path), so `findFiles('**/TCP/**/*')` silently matched nothing, and the workspace index quietly degraded to only the currently-open document(s). The same bug also explained a second reported false positive (macro-injected labels being flagged as undefined) for the identical reason — both `testCodes` and `macroLabels` come from the same broken `collectWorkspaceUris()` call. Fixed by adding `src/globMatch.js` (a small pure glob matcher, unit-tested against this exact real pattern/path pair in `tests/glob-match.test.js`) and changing the scan to `findFiles('**/*')` + manual full-path filtering, mirroring how `files.associations` actually resolves.

## Undefined data reference feature (2026-07-30)

Built (0.3.0), extending the label/GOTCP diagnostics with Reference Manual Errors 8 ("Undefined numeric") and 10 ("Undefined alpha"). `A`/`M`/`N`/`R`/`S`/`H` data-line declarations are a separate namespace from I-line branch labels ("every item of data is held in a box... identified by a LABEL" — Introduction Manual) — `src/labelParser.js`'s `findDataDeclarations` collects them, mirroring `alpha-lines`/`number-lines`/`hex-lines` exactly.

**Scoped deliberately narrow, not generic, based on real-data sampling before shipping.** The original plan was "every instruction operand that names a data label," but sampling operand1 across the top 40 most frequent non-GOTO-family opcodes in the real corpus (30,011 operand instances) showed this varies wildly by instruction — `PRINT`/`ERROR,MM`/`ADD`/`NOREPORT`/`SENDRSLT`/`DOCTOR`/`HL7NUM` and many others essentially never take a data-label operand (0-5% resolve rate; their operands are numeric literals, special CRS-parsing keywords, or something else entirely). A blanket check would have flagged roughly a fifth of all sampled operands as "undefined" — almost all false. Instead, shipped only the four keywords whose operand is genuinely, overwhelmingly a real data-label reference: **`NORMAL`, `CR TEST`, `CR CRS`, `GROUP`** (99.3-100% resolve rate each). Two plausible-looking candidates were checked and explicitly rejected:
- **`SIGNOUT`** — looked clean (0 unresolved) only because its operand is a 4-digit *test code* (e.g. `SIGNOUT 9966`), not a data label, and pure numbers were being exempted from the count for an unrelated reason. Including it would have meant "validating" the wrong thing entirely.
- **`MOVE,D`** — dominated by the special CRS-parsing keyword `VALUE` (140 of 190 instances), a different concept from a declared data box. The handful of non-`VALUE`, non-numeric cases weren't confidently one thing or another.

This list is intentionally not exhaustive — the manual catalogues 100+ instructions, and only these 4 were validated clean enough to trust. Extending the whitelist (`DATA_REFERENCE_RE` in `src/labelParser.js`) to more keywords is straightforward but should go through the same real-data sampling first.

**Resolution sources**, same layered approach as macro-label injection for GOTO: a block's own `A`/`M`/`N`/`R`/`S`/`H` declarations, any macro it invokes (macro bodies can declare data too, not just branch labels — `buildWorkspaceIndex`'s `macroLabels` now unions both), and the workspace's real `GLOBAL` file (130 lines, confirmed to be nothing but its header + comments + `A`-line declarations — every one of those is available in any block, unscoped, via a new `globalDataLabels` set in the workspace index, detected by `isGlobalDataFile`). Plus one confirmed implicit built-in, `TCPNAME` ("there is a box with the label TCPNAME. This contains the Test Name as entered on the Title line." — Introduction Manual) — likely not the only one, but the only one confirmed so far.

**A real false positive found and fixed before shipping, same bug class as an earlier one:** the first version of `DATA_REFERENCE_RE` used an unbounded `\s+` for the keyword's own trailing separator. A real line can use one of these keywords with a genuinely blank operand, followed many blank fields later by a distant trailing comment (e.g. `I NEXT GROUP <lots of blank fields> No`) — the unbounded separator let the optional operand-capture group cross every blank field in between and latch onto that far-away comment word instead of correctly reading operand1 as blank. Caught by running the real check end-to-end against the full corpus before considering it done (5 hits, all this same shape, in `HAEM`/`HISTO`/`PALMSAP`) — fixed by bounding the separator to `\s{1,4}`, just enough to finish the keyword's own 9-char field.

**Validation**: after the fix, ran the actual check against the entire real corpus (26 files) — **zero diagnostics**, matching the same standard the label/GOTCP feature was held to.

**Severity**: `warning`, not `error` (unlike undefined-label/duplicate-label) — this check is newer and, given the narrow-whitelist tradeoff above, less exhaustively validated across the full instruction set than the label feature was.

### Follow-ups (0.4.0): missing operand + matching colour

Prompted by the user testing the shipped check live: deleting a `NORMAL` operand entirely (leaving it blank) correctly didn't flag as *undefined* — a blank operand isn't a wrong reference, it's a different, unimplemented error (Reference Manual Error 7, "Missing operand"). Two follow-ups landed together:

- [x] **Missing-data-operand check**, `NORMAL`/`CR TEST`/`CR CRS` only. Validated the same way as everything else here first: counted genuinely blank-operand instances per keyword across the real corpus. `NORMAL`, `CR TEST`, and `CR CRS` have **zero** blank-operand uses across 1656 combined real instances — safe to flag unconditionally. `GROUP` was checked and explicitly **excluded**: a bare `GROUP` with no operand at all occurs **101 times** (23% of all `GROUP` usage) — a legitimate, common pattern (its own meaning, not an omission), not the same "missing operand" mistake as the other three. `src/labelParser.js`'s `findMissingDataOperands` implements this with its own `MISSING_OPERAND_KEYWORDS` set (excludes `GROUP`), separate from `DATA_REFERENCE_RE`'s four-keyword whitelist. No workspace context needed (a blank operand is wrong regardless of what's declared elsewhere). Validated end-to-end against the full real corpus: zero diagnostics.
- [x] **Operand highlighting recoloured to match its target.** Since these operands reference an `A`/`M`/`N`/`R`/`S`/`H` data label, they're now scoped `storage.testcontrolprotocol` (the same colour as that label's own declaration) instead of falling through to the generic `instruction-lines` catch-all's plain `string` colour. New `data-reference-lines` grammar rule, inserted before `instruction-lines` in the top-level `patterns` array (order relative to `goto-lines`/`search-lines`/`gotcp-lines` doesn't matter — keyword sets never overlap). **Deliberately reused the same bounded `\s{1,4}` separator as `DATA_REFERENCE_RE`** rather than the unbounded `\s+` idiom every sibling rule (`goto-lines` etc.) still uses — using unbounded `\s+` here would have reintroduced the exact same "distant trailing comment mistaken for the operand" bug into the *highlighting* layer that had just been fixed in the *diagnostics* layer for the identical keyword shape. The older sibling rules carry the same latent risk for their own keywords (GOTO/GOSUB/DATE/GET/GOTCP/SEARCH used with a genuinely blank target far from a trailing comment) — not fixed here since no real occurrence has been found for those families, but worth knowing if one ever surfaces. Covered by a new fixture (`tests/fixtures/instruction-family.tcp`, all four keywords plus the bare-`GROUP` case) and reviewed diff, not just regenerated blindly.

## PRINT op2 data reference (0.7.0)

Investigated as the top item in the audit backlog above (9,618 real uses, by far the single largest candidate found).

**The real blocker wasn't PRINT-specific — it was an entirely undocumented (to this project) third source of valid data references.** Checking why ~33% of real `PRINT` op2 values didn't resolve (`PRINT 1 TITLE` works, but `PRINT +1 DATE`/`PRINT 1 REQNO`/`PRINT 35 DRNAME` didn't) found that every single one of the 82 distinct unresolved values was an obviously meaningful system field name — never declared as an `A`-line anywhere (checked explicitly), yet clearly always valid. Traced this to the Reference Manual's "Global Data" catalogue (`Core Global Data`, `Global Data for Modules`, `Global Data in Alphabetical Order` — ~30 pages: patient demographics, request/specimen data, lab info, report-printing fields), a whole documented category of implicit boxes separate from both local declarations and the `TCP/GLOBAL` file's own constants. `TCPNAME` (already handled) turns out to be just one example the Introduction Manual happened to spell out in prose.

**Extraction problem, worked around rather than solved cleanly:** the manual's own table for this section is a multi-column PDF layout that both `pdftotext -layout` and plain `pdftotext` scramble into misaligned fragments — not reliably parseable into a clean label list. Instead of hand-transcribing ~30 pages, took an empirical approach: collected all 82 real unresolved `PRINT` op2 values from the corpus, then cross-checked each against the manual's raw text. **73 of 82 (98.9% of the 2660 total instances) appear verbatim as real manual terms**; the remaining 9 are obvious numbered continuations of already-confirmed families (`TAV1`/`TAV2` confirmed → `TAV3`-`TAV5` are clearly the same convention). All 82 were added to `IMPLICIT_DATA_LABELS` (renamed in spirit, though not in code, from "just TCPNAME" to a real curated catalogue) — this is deliberately an empirically-derived subset (what's actually used in this corpus), not a claim to the full ~30-page catalogue; extend the same way if more surface.

**A second, PRINT-specific finding:** the data reference sits at **op2**, not op1 like `NORMAL`/`GROUP`/the `CR` family — op1 is a print-column number (confirmed always numeric or blank across all real bare-`PRINT` uses, never itself a reference). Required a new regex shape (`PRINT_DATA_REFERENCE_RE`) rather than reusing `DATA_REFERENCE_RE`. Two comma-suffixed variants were checked and **handled differently**:
- `PRINT,H` and `PRINT,A` share the exact same op2-is-data-reference shape (`PRINT,H 1 DATE8`, `PRINT,A 50 SPACE 5`) — included.
- `PRINT,R` **excluded**: op2 is blank 100% of the time (349/349 real uses) — no data-reference slot exists at all.
- `PRINT,J` **excluded**: op2 only resolves ~30% of the time; real values look like literal comparison text (e.g. `PRINT,J 31 >60`), not a box reference — a genuinely different instruction despite the shared prefix.

**Validation**: new grammar rule `print-data-reference-lines` (op2 → `storage.testcontrolprotocol`, matching every other data reference), new fixture coverage for all five variants (`PRINT`, `PRINT,H`, `PRINT,A` included; `PRINT,R`, `PRINT,J` confirmed to fall through unchanged), snapshot diff reviewed. Ran the full corpus check after implementing — first pass showed 1160 false positives (`SPACE`/`STARS`/single characters), traced to a bug in the *validation script* itself (an ad-hoc harness that predated `globalDataLabels` and never passed it to `computeDiagnostics` — not a bug in the shipped code, which already passes the whole index via `extension.js`). Fixed the harness and re-ran: zero diagnostics across the entire real corpus.

## Invalid enum values render as invalid (0.15.0)

Raised directly by the user: a typo'd `NORMALX` op2 (e.g. `DATE REH` instead of `DATE REG`) correctly triggered its diagnostic, but still rendered with the neutral catch-all colour (`comment.line`, green in most themes) instead of `invalid` (red) — the grammar's op2 alternation simply didn't match the typo'd text, so it fell through to the generic trailing-content group like an ordinary comment. `SEARCH`'s item-word had the identical gap. Unlike the label/data-reference checks (which need workspace context the grammar doesn't have), both of these are genuinely fixable at the grammar level alone: both vocabularies are small, closed, and static (`NORMALX`'s 6 words, `SEARCH`'s 13), so the tokenizer itself — no diagnostics/workspace index involved — can already tell "recognized" from "not."

Fixed by splitting each rule's single optional "recognized word" capture group into a two-branch alternation: `(?:(\b(?:WORD1|WORD2|...)\b\s*)|(\S.{0,8}\s*))?`. The first branch is the unchanged recognized-word alternation (still scoped `string`); the second branch only matches when the first one fails to (regex tries alternatives left-to-right, so the fallback is never reached for a recognized word) AND there's genuinely non-blank content there (`\S` requires at least one real character, so a legitimately blank op2 field still correctly matches neither branch and falls through as before) — scoped `invalid.testcontrolprotocol`. The `.{0,8}` bound matches the same ~9-char field-width convention used throughout this grammar (covers the longest real words, `DATESPEC`/`ANTIBODY`/`DATETIME`/`REPORTED`/`TESTDEPT`, all 8 chars) and, critically, is NOT preceded by any unbounded `\s+`/`\s*`, so (like every bounded-separator fix earlier in this file) it can't skip over a legitimately blank field to grab distant unrelated content.

- Grammar only — `src/labelParser.js`/`src/diagnostics.js` untouched, since the diagnostics already correctly identified invalid values; this was purely a highlighting gap.
- `normalx-lines`: new capture group 7 (`invalid.testcontrolprotocol`) inserted before the renumbered catch-all (was 7, now 8).
- `search-lines`: new capture group 7 (`invalid.testcontrolprotocol`) inserted before the existing "criteria" group (renumbered 7→8) and catch-all (renumbered 8→9).
- **Validation**: new fixture lines (a typo'd `NORMALX` date and a typo'd `SEARCH` item word) confirm the `invalid` scope now renders correctly, diff isolated to just those two lines. Then, since the real corpus has zero invalid values by construction (already confirmed via the diagnostics validation for both features), bulk-tokenized all 2201 real `NORMALX`/`SEARCH` lines in the corpus directly through `vscode-textmate` (not just the usual snapshot fixtures) and confirmed zero of them hit the new `invalid` scope — the restructure doesn't misclassify any real, valid value.
